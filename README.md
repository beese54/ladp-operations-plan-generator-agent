# Water Network Operations Plan Generator Agent

A multi-agent assistant for water utility operators. It plans pipe shutdowns end
to end — which valves to close, in what order, on which date — and hands the
field crew a mobile checklist. The valve sequence is computed by traversing the
live network graph, not generated by an LLM; the model only parses intent and
writes the plan up in plain English.

Built for **PUB, Singapore's National Water Agency** during the AI Singapore
LADP programme (Intake 9, June–August 2026).

> This project is supported by the National Research Foundation, Singapore under
> its AI Singapore Programme.

## What it does

Three user flows share one chat interface and one LangGraph orchestrator:

1. **Ops planner** asks in plain English (*"Can I shut down pipe_084 next
   Monday?"*). The system checks scheduling rules, computes the isolation
   sequence from the graph, retrieves relevant SOPs, and generates a plan behind
   a human-in-the-loop confirmation gate.
2. **The system** books the confirmed operation, generates a PDF isolation
   report, and produces a shareable crew link.
3. **Field crew** open that link on a phone: a step-by-step valve checklist they
   tick off, with a flag button for complications. Progress flows back to the
   planner's calendar within seconds.

It also answers read-only questions — network topology (*"Which valves isolate
pipe_084?"*), supply reasoning (*"If pipe_084 is down, would valve_037 still
have water?"*), scheduling, and SOP/safety guidance.

## Tech stack

| Layer | Technology | Why |
|-------|-----------|-----|
| Agent runtime | LangGraph | Graph-driven control, checkpointing, `interrupt()` for HITL |
| Reasoning model | Azure OpenAI GPT-5.4-mini | Intent parsing + prose write-up; never the source of a valve ID |
| Network topology | Neo4j 5 (local Docker; Aura in cloud) | Pipes/valves are a graph; isolation is a traversal |
| SOP retrieval | ChromaDB + MiniLM-L6-v2 | Local, free, fast RAG over the SOP corpus |
| Scheduling rules | SQLite + plain Python | Blackout/conflict logic that must be deterministic and auditable |
| Frontend | React + Vite + Cytoscape.js | Live network rendering; mobile-first crew view |
| Observability | MLflow | Per-node tracing + custom evaluation scorers |

- **Python 3.12** with a virtual environment at `.venv`

## First-time setup

```powershell
# 1. Python dependencies (into the existing .venv)
.venv\Scripts\python.exe -m uv pip install -r requirements.txt

# 2. Frontend dependencies
cd frontend
npm install
cd ..

# 3. Environment config — copy the template and fill in your values
Copy-Item .env.example .env
# then edit .env (see the section below)

# 4. Start the local Neo4j container (one-time create)
docker run -d --name neo4j-ladp `
  -p 7474:7474 -p 7687:7687 `
  -e NEO4J_AUTH=neo4j/ladppassword123 `
  neo4j:5

# 5. Load the network into Neo4j (57 valves, 140 pipes)
$env:PYTHONPATH = "."
.venv\Scripts\python.exe scripts\restore_network_from_export.py

# 6. Ingest the SOP corpus into ChromaDB
.venv\Scripts\python.exe -m ingestion.ingest_sop
```

### `.env` values

Copy `.env.example` to `.env` and set at least the Azure and Neo4j blocks:

```dotenv
AZURE_OPENAI_API_KEY=...
AZURE_OPENAI_ENDPOINT=https://your-resource.openai.azure.com/
AZURE_OPENAI_API_VERSION=2024-12-01-preview
AZURE_OPENAI_CHAT_DEPLOYMENT_NAME=gpt-5.4-mini-pub

# Local Docker Neo4j (matches the container created above)
NEO4J_URI=bolt://localhost:7687
NEO4J_USERNAME=neo4j
NEO4J_PASSWORD=ladppassword123

CHROMA_PERSIST_DIR=./data/chroma_db
SQLITE_DB_PATH=./data/calendar.db
```

Notes:
- `AGENT_PROVIDER_SOP_AGENT` and `AGENT_PROVIDER_HISTORICAL_AGENT` default to
  `together` in code. Set both to `azure` if you do not have a Together.ai key.
- For **Neo4j Aura** (cloud) instead of local Docker, use
  `NEO4J_URI=neo4j+s://<id>.databases.neo4j.io`. Local Docker is recommended for
  development — it removes a network dependency and a demo-day failure mode.
- Never commit `.env`; it holds API keys and is gitignored.

## Running the system

Four processes. Every Python command needs `PYTHONPATH=.`, and MLflow 3.x needs
`MLFLOW_ALLOW_FILE_STORE=true` (the file store is otherwise deprecated).

```powershell
# 1. Neo4j (Docker) — start the existing container
docker start neo4j-ladp

# 2. Backend — FastAPI on port 8001
$env:PYTHONPATH = "."; $env:MLFLOW_ALLOW_FILE_STORE = "true"
.venv\Scripts\python.exe -m uvicorn api.main:app --host 0.0.0.0 --port 8001

# 3. Frontend — Vite dev server (opens on http://localhost:5174)
cd frontend
npm run dev

# 4. (optional) MLflow UI on port 5000
$env:MLFLOW_ALLOW_FILE_STORE = "true"
.venv\Scripts\python.exe -m mlflow ui --port 5000
```

Then open **http://localhost:5174**.

**Health check** (confirms all services are reachable):

```powershell
curl http://localhost:8001/api/v1/health
```

**What happens on backend startup** (`api/main.py` → `lifespan`):
1. Pings Neo4j to confirm the graph database is reachable.
2. Pre-warms ChromaDB — loads the embedding model and SOP collection into memory.
3. Bootstraps SQLite — creates tables if they do not exist.
4. Sets up MLflow tracing so every subsequent LLM call gets a trace span.

```
                    ┌───────────────────────┐
                    │   BROWSER (React)      │
                    │                        │
                    │ ChatPanel  → /api/v1/chat     │
                    │ GraphCanvas→ /api/v1/graph    │
                    │ Calendar   → /api/v1/schedule │
                    │ CrewPage   → /api/v1/crew/{id}│
                    └───────────┬───────────┘
                                │ HTTP
                                ▼
                    ┌───────────────────────┐
                    │   FastAPI (port 8001)  │◀── MLflow tracing wraps requests
                    │  api/routes/*.py        │
                    └───────────┬───────────┘
                                │
                    ┌───────────▼───────────┐
                    │  LangGraph Orchestrator │
                    │  agents/orchestrator.py │
                    │  14 nodes, conditional  │
                    │  edges, interrupt() HITL│
                    └──┬──────┬──────┬──────┘
                       │      │      │
              ┌────────▼┐  ┌──▼───┐  ┌▼────────────┐
              │  Neo4j   │  │SQLite│  │  ChromaDB   │
              │ (Docker) │  │ ops  │  │ 85 chunks   │
              │ 57 valves│  │ cal  │  │ from 9 docs │
              │ 140 pipes│  │ crew │  │ MiniLM-L6-v2│
              └──────────┘  └──────┘  └─────────────┘
                       │      │      │
                       └──────┼──────┘
                              ▼
              ┌───────────────────────────────┐
              │   Azure OpenAI (GPT-5.4-mini)  │
              │   intent parsing · plan write-up│
              └────────────────────────────────┘
```

The graph is built once at startup (`get_graph()` in `orchestrator.py`) and
reused for every request. State is persisted per `session_id` in SQLite
(`checkpoints.db`), which is what makes clarification round-trips and the booking
confirmation gate work across separate HTTP calls.

## How a chat message flows

```
Browser (ChatPanel.jsx)
    │  POST /api/v1/chat  { session_id, message }
    ▼
FastAPI (api/routes/chat.py)
    │  mlflow tracing → invoke_graph(message, session_id)
    ▼
LangGraph Orchestrator (agents/orchestrator.py)
    │  intent parse → route → agents → response
    ▼
FastAPI builds ChatResponse { message, feasibility, pipe_id, answer_path, ... }
    ▼
Browser renders the reply (and may auto-trace the graph / switch to calendar)
```

`api/routes/chat.py` is the glue: it receives the POST, calls `invoke_graph`,
handles the interrupt/resume pattern when the graph paused for clarification,
builds the response the frontend needs, and logs to MLflow.

## The five chat paths

`invoke_graph` classifies intent, then routes to one of five paths. Some paths
are intercepted deterministically *before* the intent parser to guarantee correct
handling regardless of LLM variability (crew restriction, supply questions, the
stored-steps request).

**A — Operations planning** (the main flow)
`intent_parser → clarification (if slots missing) → neo4j_agent → parallel
fan-out (calendar + sop + historical) → ops_plan_generator → response →
booking_gate`. The valve sequence comes from a Neo4j traversal; the calendar
agent uses no LLM; booking is behind a human confirmation `interrupt()`.

**B — General question** (SOP, system info, topology)
`general_response_node`, three tiers in order:
1. `system_knowledge.py` — deterministic answers derived from real engine
   constants (scheduling rules, duration sizing, crew features).
2. `topology_answers.py` — live Neo4j lookups (isolation chain, pipe properties,
   valve turn count, supply/alternate-feed reasoning).
3. `_sop_grounded_answer()` — ChromaDB retrieval + LLM synthesis, with a
   grounding post-check and a source-attribution footer.

**C — Out of scope**
`off_topic_node` — rechecks system-knowledge and topology (the classifier is
fuzzy at the UNKNOWN/GENERAL boundary), otherwise returns a fixed decline string
with no LLM call.

**D — Schedule query**
`schedule_query_node` — reads SQLite and formats a table of what's booked.

**E — Crew page chat**
Same `/api/v1/chat` endpoint. The crew page prefixes messages with
`[FIELD CREW ...]`; ops *commands* (booking, scheduling) are refused while
*questions* (SOP, troubleshooting, supply checks) are answered.

## Frontend layout

**Main app** (`http://localhost:5174`) — a two-panel layout:

```
┌──────────────────────────────┬───────────────────────┐
│  LEFT PANEL (60%)            │  RIGHT PANEL (40%)     │
│  [Network Graph] [Ops Cal]   │  Chat Panel            │
│                              │                        │
│  Tab 1: Cytoscape network    │  Message bubbles       │
│  Tab 2: month calendar grid  │  Input box + Send      │
└──────────────────────────────┴───────────────────────┘
```

- **Network graph** loads from `/api/v1/graph` and renders with Cytoscape.js.
  Typing a pipe ID and tracing (or asking about a pipe in chat) highlights the
  isolation chain in yellow/orange via `/api/v1/trace/{pipe_id}`.
- **Ops calendar** loads from `/api/v1/schedule/month`, shades holidays and
  blackout dates, colour-codes planned vs emergency, and shows crew progress. It
  polls every 15 seconds so on-site updates appear without a manual refresh.
- **Crew page** (`/#/crew/OPS-XXXXXXXX`) is a separate mobile-first page — no
  graph, no calendar — routed by URL hash (no React Router dependency).

## Where the guardrails live

Guardrails *restrict* behaviour. Routing decisions (which correct answer to give)
are separate and are not guardrails.

| # | Guardrail | File |
|---|-----------|------|
| 1 | Intent classification → UNKNOWN takes the decline path | `agents/orchestrator.py` · `intent_parser_node` |
| 2 | Off-topic decline, deterministic, no LLM | `agents/orchestrator.py` · `off_topic_node` |
| 3 | Closed capability list in the system prompt | `agents/orchestrator.py` · `_GENERAL_SYSTEM` |
| 4 | Output regex backstop for claimed banned capabilities | `agents/orchestrator.py` · `_claims_banned_capability()` |
| 5 | Content grounding check on RAG answers | `agents/orchestrator.py` · `_answer_is_grounded()` |
| 6 | Live-data exclusion (never serve stored values as sensor readings) | `prompts/topology_answers.py` · `_LIVE_DATA_WORDS` |
| 7 | Crew read-only (questions allowed, ops commands blocked) | `agents/orchestrator.py` · crew restriction in `invoke_graph` |

> The crew read-only restriction is a UX safety net, not an authorisation
> control — the `[FIELD CREW ...]` prefix is client-supplied and there is no
> auth. Hardening it is tracked as future work.

## Evaluation and robustness

- **Probe harness** (`scripts/probe_chatbot.py`) runs a 58-question bank across
  four personas, auto-classifies each answer, and computes RAG Triad scores per
  answer path. Outputs land in `data/probe_results/` (gitignored).
- **Scorers** (`evaluation/scorers.py`) — 9 deterministic scorers including the
  RAG Triad (context relevance, groundedness, answer relevance) plus answer
  correctness against SME ground truth. Token-overlap based, so they are free to
  run and reproducible. Reported **per answer path** because the deterministic
  paths score groundedness 1.0 by construction and would inflate a blended
  number.
- **Robustness** (`tests/test_robustness.py`) — SQL/Cypher/prompt injection, XSS,
  10k-char input, null bytes and rapid-fire, with database-integrity checks after
  each injection.

## Troubleshooting

| Symptom | Likely cause / fix |
|---------|--------------------|
| `ModuleNotFoundError` on any script | `PYTHONPATH` not set. Prefix with `$env:PYTHONPATH = "."`. |
| MLflow errors about a deprecated file store | Set `$env:MLFLOW_ALLOW_FILE_STORE = "true"`. |
| Backend health check shows Neo4j unreachable | The `neo4j-ladp` container isn't running — `docker start neo4j-ladp`. |
| Chat replies "not part of the documented procedure" for a valid SOP question | Corpus not ingested — run `python -m ingestion.ingest_sop`. |
| Network graph is empty | Network not loaded — run `scripts/restore_network_from_export.py`. |
| `pip.exe` blocked by application control | Use `uv pip install` instead of plain `pip`. |
| Frontend can't reach the API | Confirm the backend is on port 8001 and the Vite proxy points there. |
